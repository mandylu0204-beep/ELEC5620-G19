## 4. 建议统一为阻断 → 审核 → 修订 → 可最终化的主状态优先级

建议接受 B 的主状态优先级：`BLOCKED > ESCALATED > REVISION_REQUIRED > ELIGIBLE_FOR_FINALISATION`，符合此前“高风险、低置信度或未解冲突进入审核”的业务约定。

A 负责同步实际路由判定和 proposed_route 校验的优先级，不能仅修改前端展示。页面同时展示全部 blockers、审核要求和修订要求，不用单一主状态隐藏超预算等未解决条件。

例如高风险与超预算同时出现时，主状态建议为 ESCALATED，同时列出预算修订要求。即使审核批准，仍需满足预算及其他放行条件；批准不是最终化，修订后新版本/新 run 的旧审批不能自动沿用。

此项是建议的新统一行为，当前 A 代码仍为修订优先。强制 blocker 始终最高，人工审核不能覆盖必要证据缺失或道路关闭等硬阻断。

## 5. 恢复边界接受，但补充成功提交的时机

A 负责调度、进程退出/启动恢复、过期检查、显式 retry 和 attempt fencing；B 负责读取 checkpoint、复用已保存产物、仅执行缺失步骤。现有接口基础可复用，不重做。

A11 在启动时恢复 PENDING；RUNNING 要等租约过期，再在启动扫描或当前 run 的页面读取中标记失败，用户通过详情页重试。当前不是持续运行的全局过期扫描服务，不应声称无需任何触发就会自动恢复所有运行。

B 的协作式 heartbeat 可保留；A supervisor 也自动续期。B 应使用非阻塞调用，响应取消，并依据 A 实际租约设置合理间隔。

需要额外统一以下完成语义：

1. B 调用 report_stage(COMPLETED, SUCCEEDED, None) 表达完成意向并校验前提；在 A11 dispatcher 使用的端口上，数据库仍为 RUNNING。
2. B 返回符合契约且引用正确已保存产物的 RunResult；A 校验后持久化 SUCCEEDED。
3. 最终 eligibility 由 A 在实际提交后重新计算，通过查询接口供页面读取。B 不自行调用 commit_success，也不把完成意向后的 RUN_NOT_SUCCEEDED 当成最终 blocker。

独立组合测试已观察到：A 最终运行成功且可最终化，但 B 的返回 blockers 仍包含提交前 RUN_NOT_SUCCEEDED。请 B 根据上述时机调整最终返回/异常描述，并与 A 一起添加带 context_provider 的 RecoveryPort 和真实 HTTP 联调测试。不能仅沿用没有 dispatcher 的 WorkflowService 测试推断完成事件已落库。

SUCCEEDED 只表示本次执行及保存完成；安全评估结果、审核决定、版本路由和 FINALISED 各自独立。
