# 附录：完整接口约定


日期：2026-10-15。状态：A 侧已整理，待 B 复核并实现。本文不是已实现功能说明。

## 目标和边界

正常产品流程不要求用户选择内部 safety_case_id，不在表单中锁定某几个演示日期。后端依据已确认需求和实际选中营地选择资料。有限数据之外如实报告不足，不放宽审核、最终保存或未知值处理。

现有问题有两层：启动时只登记一个场景，改营地后无法使用其他已存在的记录；封存 v2 的正常资料本身也只覆盖少量日期。两个问题都需要修复。不能仅登记所有 safety_case_ids：现有 scenario_for 只按营地过滤，再对所有记录日期取交集，跨日期记录会制造空交集或伪冲突。

## E-01：版本与共同输入

保留共享 contracts/schema 1.0、保存端口签名和已有数据库结构。由 B 实现只读的内部业务选择器，建议入口如下，类型位于 B 的业务模块，不加入共享 DTO：

```python
resolve_trip_evidence(
    confirmed_requirements: ConfirmedRequirements,
    campsite_ids: Sequence[str],
    demo_context: DemoContext,
) -> TripEvidenceSelection
```

选择器绑定 A 在本次 run 开始前登记的不可变数据快照。实际营地在模型生成后才确定，因此不能把“先选中营地才能登记 run”作为前置条件。A 预先登记完整资料索引摘要、选择策略版本及检查时钟；B 从这个快照中确定性查询。恢复时不得临时切换到更新的数据。

## E-02：返回形状

建议返回以下内部字段；B 如需调整命名请在实现前说明，但语义保持一致：

| 字段 | 含义 |
|---|---|
| `selected_case_ids` | 真正采用的来源记录，稳定排序，不含测试 oracle |
| `scenario_context` | 供已有 SafetyInput 使用的 ScenarioContext，保留逐条资料的营地、来源和日期 |
| `weather_facts_by_campsite` | 各营地可用于装备规则的已知天气事实；未知仍为 null |
| `coverage_issues` | 结构化的营地、资料类别、原因、覆盖范围和未覆盖范围 |
| `selection_digest` | 选择规则、查询及选中资料的规范化摘要，不能包含自身 |

`coverage_issues` 建议包含 `campsite_id`、`kind`（WEATHER/FIRE/ROAD/RESTRICTION）、`code`（MISSING/OUTSIDE_VALIDITY/NOT_YET_OBSERVED/STALE/CONFLICTING/ROAD_STATE_UNKNOWN）、请求起止日期、可用日期范围和缺口范围。资料质量问题与道路/营地关闭等业务限制分别返回；“完整资料明确写着关闭”不能被说成“缺资料”。这些字段只做内部与 A-owned HTTP 扩展，不能任意塞入现有严格 model trace。

## E-03：选择、日期及冲突

1. 先按实际营地筛选，再按行程日期、观测时间和检查时钟匹配；不能仅按场景编号、固定输入文字或预期结果选记录。
2. 来源日期、观测时间与有效期分别核对。尚未发布/观测的资料不得因有效期匹配而被提前使用；固定演示时钟独立于电脑日期。
3. 每个营地、每种必要资料分别验证行程覆盖。不同营地或不相交日期的记录不能被当作互相冲突。
4. 如果实现跨多个区间拼接，必须验证区间没有缺口、来源可比较，并保留全部区间；不能把并集直接当作连续有效期。首版如仅支持单条完整覆盖，应明确报告部分覆盖，不能谎称无缺口。
5. 对同时适用但互相冲突的来源，不能静默选择较有利的一条。若有可信的替代/修订关系，须有显式元数据及确定规则；仅凭日期较新不能自动解除冲突。
6. 多营地行程只有在实际住宿安排的日期映射明确时才按各住宿段匹配，否则保守要求覆盖整个行程。不得根据营地列表臆测住宿日期。

## E-04：业务和恢复一致性

装备天气输入与安全证据必须来自同一选择结果。PLAN、REVISE、REASSESS 使用相同的选择策略；REVISE 根据新营地重新查询，REASSESS 保留原行程但创建新评估。用户资料变更仍需重新确认，不能借重评偷偷应用未确认的新 Profile。

选中记录及原始来源需反映在已有产物 source_refs 中。任何影响结果的数据/选择策略变化应进入运行身份，旧任务不得继续使用新身份。A 继续负责运行登记、事务、幂等、checkpoint、权限与最终保存；B 不直接改变 FINALISED 或 eligibility。

不增加“运行失败后换资料凑通过”的回退。不重复调用模型补丢失 trace，物流不可恢复审计错误不得提升为 RETRY。当前物流模型 502 为独立问题，不能以新增资料选择器替代该问题的真实验收。

## E-05：正常应用数据与异常测试

由 B 基于封存 v2 新建独立版本，不覆盖已验收的 v2。为现有 10 个营地建立连贯的基础资料，覆盖商定的常见短途日期范围；数值、来源、适用范围、费用和设施保持一致，synthetic 身份不变。不得无限延长天气有效期、把未知费用当零或默认所有营地开放。

缺失、过期、相互冲突等故意构造的 fixture 保留在明确的测试入口，与正常资料索引隔离；正常用户查询不能因误加载多个互斥测试世界而产生伪冲突。数据本身明确记录的真实场景限制仍按日期和营地正常应用，不能为了演示移除。

B 交付：来源文件与封存 manifest、覆盖清单、迁移说明、静态检查报告、选择器规则/恢复测试。A 负责数据根目录和 manifest 核验、工厂接线与设置身份登记；在 B 确认返回结构前不预先编造空选择器或默认成功实现。

## E-06：页面及资料不足

A 已实现重评进度/完成时间/同版本对比的只读反馈，以及资料变化与服务不可用的独立提示。前端不添加内部场景选择器，也不把数据不足归咎于用户未填写必填项。

B 提供结构化覆盖结果后，A 再展示具体缺什么及可验证的替代营地/日期。替代方案必须经过实际资料查询及原预算、设施等条件核对；不自动修改用户需求，不把“有安全资料”说成“预算和装备全部通过”。当前最接近营地组件仍只在既有 NO_MATCH 流程工作，不声称已支持安全缺口的替代搜索。

## E-07：联合验收门槛

- 普通用户在同一个应用实例中换营地，无需改后台场景配置即可查到相应资料。
- 覆盖范围内日期调整、跨界日期、部分覆盖、多营地、未来观测、重叠冲突和资料明确关闭分别验证。
- 缺失资料完成一次检查后仍不可最终保存；重复检查给出“结果一致”，不伪造已解决。
- 新运行使用新资料；历史回读保持原记录，旧审批不继承；恢复不重复保存或重新调用已完成模型步骤。
- 正常、预算修订、缺资料、道路关闭执行实际 HTTP/浏览器验收；模型物流 502 单独复测。
- 前端类型/构建、共享 schema、数据静态检查、相关后端回归及 Canvas 全新目录启动验证通过后，才作为可交付版本合入 main。
