## 二、已确认未解决的问题

### U-01：营地供水未知时的自带水处理政策不完整

**现象**：选择 Cockatoo Island 后，装备与费用检查保留饮用水相关澄清项，不能完成最终保存资格所需的全部检查。

**已确认原因**：

- `data/sydney_surrounds_v2_2/data/synthetic_campsites.csv` 中该营地 `potable_water=unknown`。
- `source_catalogue.json` 对应字段为 `UNKNOWN`／null。资料包的来源备注表示有开水设施信息，但没有确认可自由取用的饮用水供应；这不是对现实营地现状的重新核实。
- 物流代码遇到未知供水会直接增加营地资料澄清项；装备规则同时依赖 `potable_water`，又增加一个未知输入澄清项。
- 当前代码即使按保守方式计算饮水准备，也仍保留上述未知供水澄清。不能简单通过修改个人资料将其清除。

**影响**：这是营地资料字段未确认及其业务处理政策的问题，SQLite 记录正常。用户可能已经登记足量饮水，仍被要求等待系统资料处理。

**建议方案，需先确定政策再实施**：

1. 保持原营地供水字段未知，不把它改成“有水”或伪装为已核实。
2. 评估新增有版本身份的保守自带水处理：系统沿用批准的模拟用水规则计算需求，并核对用户实际确认的数量和可用状态。
3. 足量时可考虑消除“必须依赖营地供水”的物流缺项，同时保留“营地供水未核实、本次按自带水准备”的说明。其他安全证据、天气、审核及最终保存守卫仍独立判断。
4. 自带水不足、数量未知或未确认时，继续明确提示，不能清空 blocker 或代替用户确认。
5. 如果改走补充来源资料的路线，按新数据版本发布并保持旧快照；不直接修改封存包来迎合案例。

**建议分工**：B 提出物流政策与计算接线，数据负责成员维护来源，A 复核正式评估、身份、恢复和最终保存影响。

**验收要点**：供水 True／False／未知、自带水足量／不足／未知／未确认均覆盖；旧快照和审计不变；不能因此放宽其他安全检查。本文不提供实际露营饮水安全标准。

### U-02：同一供水问题出现两条相同的泛化待办

**现象**：页面连续出现两张“系统资料需要补充”，用户看不出缺的是什么。

**已确认原因**：同一评估分别返回：

```text
campsite.cockatoo-island.potable_water
gear_rule_input.potable_water
```

两项最终都投影为 `SOURCE_DATA`，前端使用同一套通用文案。它们来自同一个供水未知事实，不是两份独立数据丢失。

**建议方案**：通过结构化字段建立共同问题归属，展示为一项“营地饮用水供应尚未确认”，说明影响、来源及可采取的动作；在技术详情保留两条原始检查记录。不能只删一条原始评估或解析英文错误字符串来猜测归属。

**验收要点**：同源问题合并展示，不吞掉其他营地或其他字段的问题；历史／最终快照的原始记录仍可追溯。若 U-01 尚未实现，不提供虚假的“确认已解决”按钮。

### U-03：必要装备补缺费用缺少参考价或映射

**现象**：自行烹饪且燃料需要补充时，可能出现“系统缺少适用报价”，导致总费用不能完整确定。

**已确认原因**：`backend/app/agents/rules/logistics.py` 的 `GEAR_COSTS` 没有 `fuel_canister` 对应的适用费用映射。必要装备存在缺口、又没有匹配费率时，代码保留未知单价及未知小计，不按零费用处理。其他未映射的必要装备缺口也可能进入同一路径。

**影响范围**：不是所有自炊方案都会缺价。若相关装备实际已备齐、数量足够且已确认，可能不再需要该项补缺费用；用户不能虚报拥有状态来消除费用。

**建议方案**：核对现有必要装备与费用覆盖，补充带单位、适用范围和版本身份的模拟参考价及代码映射；由数据发布负责成员按正式版本维护，不改原封存包。明确报价只是估算，不代表已购买、已租借或已预订。

**验收要点**：缺口、无缺口、未知库存、未知单价、单位不匹配、整数分／Decimal 计算及预算判断均覆盖；借用／拟购买不能自动变成已拥有或免费。

**与当前供水截图的区别**：最近供水问题那次物流评估费用行均已计算，总额为 AUD 318.00；它的两条提示不是缺报价。不要把两种问题混成同一个故障。

### U-04：营地比较缺少差异化信息

**现象**：选中营地和其他候选都显示“地区、容量和必须条件匹配”等相同理由。

**已确认原因**：候选筛选理由由规则生成，所有合格候选首先获得同一句共同入选依据；只有已支持且有来源对应的偏好才增加具体理由。前端按各自候选读取，没有证据表明它错误复制了同一个营地的数据。模型选中某个营地的意见另存，不等于已为每个候选生成独立解释。

**建议方案**：共同条件集中展示，逐营地比较保存结果或其绑定来源支持的营地费、交通接入、设施、限制和未知项。明确区分“规则事实”“模型意见”和“待确认信息”。不为制造差异增加无依据文字，不自动翻译或重新调用模型修改旧记录。

**验收要点**：不同事实展示不同值；相同事实允许相同；未知保持未知。比较必须绑定本次保存的数据身份，不能拿当前资料改写旧选择理由。

### U-05：文本框允许自由表达，但系统只对有限条件有可验证支持

**现象**：用户输入“轻松的行程、减少爬升”等偏好后，多处出现无法验证的提示；自由填写必须条件时，用户不容易知道哪些表达能成为正式筛选条件。

**当前状态**：用餐方式已有明确选择；已有部分术语映射及需求确认校验。但偏好和必须条件仍主要是文本框，有限映射无法覆盖任意自然语言，也不能弥补缺少爬升／路线资料的问题。提前报错本身不能解决输入体验。

**建议方案**：

- 已支持的必须条件提供可理解的结构化选择，以稳定字段编码保存，页面语言可独立切换。
- 保留其他需求说明，摘要区区分“已转成可验证条件”和“仅记录、暂不能验证的要求”，由用户确认。
- 对减少爬升等需求，先确定是否补充有界模拟数据和相应规则；没有来源时不能声称已满足。
- 不通过不断增加中文同义词、悄悄删除未知需求或让模型自行宣称满足来代替能力设计。

**验收要点**：未知、否定、复合及矛盾条件不被误解；未支持条件不能冒充硬性匹配；不自动修改用户已确认要求。

### U-06：预算内完整方案搜索能力尚未实现

**当前已完成**：超预算待办已接入“保持预算，寻找更低费用方案”，旁边保留独立修改预算入口；需用户确认才执行修订。

**剩余限制**：现有修订目标优先寻找单晚营地费更低的营地，再进行完整评估。便宜营地可能有更高交通费、补缺成本或未知费用，所以总额仍可能超预算。模型调整费用优先级不会产生折扣或改变参考单价。

**建议方案**：先提供完整费用组成、降费可能性及无可行方案的明确说明；如要保证在预算内寻找候选，再单独实现有来源约束的全行程费用比较／搜索。不得擅自提高预算、删除必要费用或把未知费用填零。

**验收要点**：有可行低价候选、所有候选仍超预算、未知费用、营地便宜但总费用更高等情况均准确说明。
