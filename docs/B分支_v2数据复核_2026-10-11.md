## D-01：实际交付包的 manifest 校验失败，需要 B 修复

已阅读脚本后，以不写报告、不生成 pycache 的方式运行：

```text
python -B scripts/validate_dataset.py
```

实际退出码 1，结果：**67 项通过、1 项失败，58 条应用规格未运行**。失败的 Release manifest checksums 列出两个文件问题：

1. `scripts/__pycache__/runtime_inputs.cpython-314.pyc` 登记在 manifest 中，但 Git 不包含该文件。它是机器/解释器生成的缓存，不应成为发布包的必需封存对象。
2. `tests/synthetic_agent_test_cases.csv` 实际 Git 文件的 SHA-256 与 manifest 不一致：

| 摘要 | 值 |
| --- | --- |
| manifest 记录 | `f80d1557065d168de6541d375b623cece20d6f83ee01fa803639cc9e41b52c8f` |
| 实际交付字节 | `bde00a11bd0c0482ac1b1128b4639a68ef11c9639ed33e7d74713a0125bf6026` |

独立验证：将实际 LF 文件转换为 CRLF 后，摘要恰好匹配 manifest。仓库 `.gitattributes` 使用 `* text=auto eol=lf`，只对旧 `data/synthetic_demo/**` 设置了保留字节规则，新 v2 未设置例外；本次封存使用了 Git 换行规范化之前的字节。

`repair_review_findings.py` 的 ROOT.rglob() 会把运行产生的 pycache 一并封存；提交时这些文件被忽略，从而产生只在作者机器上满足的 manifest。

请 B：

- 封存只包含实际发布的文件，显式排除 `__pycache__`、`.pyc` 和其他运行产物，不靠加入缓存文件修复。
- 明确采用固定 LF 或保留包字节的策略，使写入、Git、ZIP 和校验使用相同字节；不要静默跳过 CSV 摘要比较。
- 基于干净 Git 快照重新生成 manifest，并实际运行校验；同步最终报告和机器可读静态结果。
- 验证 GitHub 下载 ZIP 或 git archive 解压后的包，而不只校验生成脚本所在工作目录。

因此当前包内 FINAL_VALIDATION_REPORT.md 的“68 项通过，0 项失败”不能直接用于描述 Git 下载副本。当前 A 身份检查只校验实际消费的业务/runtime/场景文件；本次两个问题不在其消费范围，因此 A 身份检查通过不代表整包封存通过。

用 A 当前 inspect_dataset() 只读检查该包，成功识别 2.0.0、v2 来源及 9 个输入摘要（六份业务文件、两份 runtime 文件、manifest）。
